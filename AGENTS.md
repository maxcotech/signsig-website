# SignSig — the constitution

**Read this file first, every session, before touching any code.** Nothing here
is optional. `CLAUDE.md` is a pointer to this file.

You are implementing **one page or one section** of the SignSig marketing site
from a **single desktop PNG**. You have no memory of previous sessions and the
next session will have no memory of yours. The repository is the only channel
between you. That is why the documents matter as much as the code.

## 1. The five rules most often broken

Read these even if you read nothing else.

1. **Never write a colour literal.** No `#30A46C`, no `rgb()`, no `bg-[#fff]`.
   Colours come from semantic tokens: `bg-primary`, `text-muted-foreground`.
   `npm run check` fails the build on violations.
2. **Never exceed 150 lines** in any file under `src/app/`, `src/components/`
   or `src/features/`. ESLint errors, it does not warn.
3. **A desktop PNG is not permission to ship desktop-only markup.** There is no
   mobile comp and there never will be. You derive tablet and mobile using the
   doctrine table in `docs/RESPONSIVE.md`. A section that only works at 1440px
   is **not finished**.
4. **Search before creating.** Duplicate components are the single most likely
   failure mode across parallel sessions. Follow §4 below.
5. **Transcribe copy exactly.** The words in the PNG are the indexed content.
   Never paraphrase, never lorem-ipsum, never "improve" it. If text is
   illegible, **stop and ask** — do not invent.

## 3. The token system, and the escape hatch

Three layers, all in `src/app/globals.css`. Full detail in
`docs/DESIGN-SYSTEM.md`.

- **Layer 1 — Primitives.** `--brand-1..12`, `--neutral-1..12`, etc. Named for
  what they _are_. **The only place in the repository where a raw colour
  literal may appear.** Primitives never flip between light and dark.
- **Layer 2 — Semantic.** `--primary`, `--muted-foreground`, `--border`. Named
  for their _role_. These flip. This is what components consume.
- **Layer 3 — Usage.** Tailwind utilities in `.tsx`. `bg-primary`. Nothing else.

Tokenised in the same spirit, and equally binding: **type scale**, **spacing**,
**radius**, **shadow**, **z-index**, **motion**. `z-[9999]`, `duration-[437ms]`
and `text-[42px]` are the same failure as a hardcoded hex.

### The escape hatch

> A colour that appears in a design PNG and is not in the token system means
> **the token system is incomplete**, not that the component needs a hex code.
> Add the value to the primitives layer, map it to a semantic token, document
> it, then consume the token.
>
> If a raw value is genuinely unavoidable, it goes in the primitives file with
> an `/* ESCAPE: <reason> */` comment. **It never goes in a component file.**

There is exactly one non-CSS exception, already built and allowlisted:
`src/lib/raw-colors.ts`, for consumers that are not CSS engines and therefore
cannot resolve a custom property — browser/OS chrome (`themeColor`) and
`next/og` images (Satori). Read that file before adding to it. Do not use it as
a general bypass; if the colour is consumed by CSS, it belongs in the token
system.

### Adding a token — all three places, or it does not work

1. Primitive in `:root` (Layer 1).
2. Semantic token in **both** `:root` **and** `.dark` (Layer 2).
3. One `--color-<name>: var(--<name>);` line in the `@theme inline` bridge.

Miss step 3 and the token exists but no utility class does. `npm run
check:tokens` verifies all three mechanically.

## 4. Anti-duplication protocol

Before creating **any** component, in this order:

1. Read `docs/COMPONENTS.md`.
2. `rg` the codebase for the concept **and its synonyms** — `card`, `tile`,
   `panel`, `box`, `item`, `cell`.
3. Check `src/components/ui/` — shadcn may already ship it
   (`npx shadcn@latest add <name>`).
4. Check `src/components/common/` and `src/components/layout/`.

If something similar exists: **extend it via props or `cva` variants, do not
clone it.** If extending would make it incoherent — a genuinely different
responsibility, not merely different padding — create the new component and
record in `docs/DECISIONS.md` why the existing one did not fit.

If a feature-local component is now used by a second feature, **promote** it to
`src/components/common/`, update all imports, and update `docs/COMPONENTS.md`
**in the same change**.

**Do not hand-write or hand-edit anything in `src/components/ui/`.** It is CLI
output. To add project behaviour to a primitive, wrap it in `common/` — see
`src/components/common/action-button.tsx` for the worked example.

## 5. The 150-line ceiling

Enforced by ESLint `max-lines` on `src/app/**`, `src/components/**`,
`src/features/**`. Exempt: `src/components/ui/**` (CLI-generated).

The rule is a **detector, not the goal**. A file crossing 150 lines is a
symptom. The correct remedies:

- Repeated block → extract a reusable component.
- Stateful logic → extract a custom hook.
- Static data (nav items, feature lists, FAQ copy) → a colocated `*.data.ts`.
- Pure transforms → `src/lib/`.

**Split by responsibility, not by line count.** `hero-section-part-2.tsx` is
this rule violated with extra steps.

## 6. Per-session workflow

1. Read the docs in the pre-flight checklist.
2. Follow `docs/DESIGN-TRANSLATION.md` **step by step**, in order.
3. State your component plan and responsive derivation plan **before** coding.
4. Implement. Server Components by default; `"use client"` only on the
   interactive leaf, pushed as far down the tree as it goes.
5. Self-review against the checklist in `docs/DESIGN-TRANSLATION.md` step 6.
6. Run `npm run check`. It must pass clean.
7. Update `docs/COMPONENTS.md`. Append to `docs/DECISIONS.md` if you deviated.
8. Report: what was built, files touched, tokens added, components reused vs.
   new, **every responsive derivation you made**, and every assumption.
9. **Then ask** whether to run a visual test. Do not start a dev server,
   launch a browser, or take screenshots without an explicit yes.

## 7. Definition of done

A session is not finished until **all** of these hold:

- [ ] `npm run check` passes clean (typecheck → lint → colours → tokens → build).
- [ ] Zero hardcoded colours, spacing, type sizes, z-indexes or durations.
- [ ] Every file under 150 lines.
- [ ] Matches the design at **1440px** — the only width where "matches the
      design" is a meaningful claim.
- [ ] Tablet and mobile derived per `docs/RESPONSIVE.md`; every deviation from
      the doctrine table logged in `docs/DECISIONS.md`.
- [ ] No horizontal overflow at 360, 390, 768, 1024, 1280, 1440, 1920.
- [ ] Reading order after collapse follows the desktop visual hierarchy, and
      **source order matches** — no `order-*` patches.
- [ ] Keyboard navigable, visible focus, sensible tab order, interactive
      targets ≥44×44px, `prefers-reduced-motion` respected.
- [ ] SEO checklist in `docs/SEO.md` complete; route added to
      `src/config/routes.ts`.
- [ ] `docs/COMPONENTS.md` updated.
- [ ] Copy transcribed verbatim from the PNG.
- [ ] Every assumption listed in the final report.

## 9. Ambiguity policy

A desktop-only PNG under-determines a great deal: hover, focus, active and
disabled states; loading, empty and error states; tablet and mobile layout;
overflow with longer strings; scroll and entrance motion; illegible text.

Follow the doctrine table where it applies. Choose the most reasonable option
where it does not. Then **list every assumption in your final report** so the
user can correct it. Never present an assumption as if it were in the design.

When an assumption is both **consequential and cheap to check** — the mobile
treatment of the primary navigation, whether a hero visual survives at 360px —
**ask before building**, not after.

If a rule here conflicts with a current best practice in the installed
versions, **follow the better practice and record the deviation in
`docs/DECISIONS.md` with your reasoning.** Correctness wins over compliance.
